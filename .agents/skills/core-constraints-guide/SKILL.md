# 坦克保卫战核心约束速查

> 这些规则**不可妥协**，违反即视为 bug。

## 1. 错误不可掩盖

禁止用以下方式绕过错误：

- 过度 `pcall` 包裹
- 默认值兜底（`result or default` 隐藏 nil）
- 注释掉报错代码
- `return` 提前退出绕过异常路径

**内部逻辑必须让错误正常暴露**，仅允许在外部边界（网络请求、用户输入等）做必要容错。

```lua
-- 错误：掩盖错误
local ok, result = pcall(some_func)
if not ok then return 0 end

-- 错误：默认值兜底隐藏 nil
local value = get_config(key) or 0

-- 正确：让错误正常暴露
local result = some_func()
local value = get_config(key)  -- 如果 key 不存在应该报错，而非静默返回 0
```

## 2. 改动数字需有依据

不得随意调整配置数值、参数、版本号。

调整前必须明确：
1. **原因**：为什么要改这个数字？
2. **目标值**：新值是多少？
3. **依据**：基于什么测试/计算/文档？

不确定时先查文档或询问用户。

```lua
-- 错误：凭感觉调数字
local WAVE_INTERVAL = 30  -- "感觉30比较好"

-- 正确：有依据的调整
-- 依据：easy→normal 难度梯度，场地 24→18 缩小 25%，波次间隔同步缩短 25%（40→30）
local WAVE_INTERVAL = 30
```

## 3. 改动已有代码前先汇报

**修改现有代码（非新增）前必须向用户说明：**
1. 文件路径
2. 修改位置（行号/函数名）
3. 原内容 → 新内容
4. 修改原因

经批准后方可执行。**新增代码无需汇报。**

## 4. 求助阈值

同一问题尝试 **2 次**仍未解决，**必须主动向用户请求帮助**。

请求时需提供：
1. 问题描述
2. 涉及文件路径
3. 当前相关代码调用关系梳理

不要盲目重试或绕过。

## 5. 添加功能前必须先探索

**不要凭局部理解直接写新代码。** 添加任何功能前，必须按以下顺序执行：

### 步骤 1：搜索已有代码

在整个项目中搜索与需求相关的已有函数、变量、事件处理。

### 步骤 2：通读相关函数的完整流程

理解数据流、调用链、UI 结构，**不要只看片段**。

### 步骤 3：确认复用/扩展哪个已有结构，再动手

优先找功能类似的代码复制模式，而不是新建。

### 具体场景

| 需求 | 正确做法 | 错误做法 |
|------|---------|---------|
| 加检查/奖励逻辑 | 先搜已有的检查/奖励函数，看能否合并进去 | 新建独立函数 |
| 加 GUI | 先看同页面的现有元素格式，保持一致 | 单独开 frame |
| 加事件处理 | 先找已有的事件处理代码，看放在哪里最合适 | 新建独立文件 |
| 修改函数后 | 必须验证编辑结果，确认改动生效 | 假设改动生效 |

### 反面案例

- 不要新建独立函数，如果已有同类函数可以合并
- 不要单独开 GUI frame，如果同页面已有列表可以加入
- 不要加 `game.print` 全局公告，除非确认不会重复执行且确实需要
- 不要在没通读完整函数流程前插入代码，容易插入到错误位置

## 6. 作用范围上限 24 米

**任何魔法技能、天赋的作用范围，最大有效值就是 24 米。**

- 若计算或配置出的范围超过 24 米，一律按 24 米处理
- 代码中相关数值只能写 `24`，不得写更大的数
- **非魔法技能，或者天赋，不受这个限制约束**

```lua
-- 错误：魔法技能范围超过 24
local MAGIC_RANGE = 30

-- 正确：魔法技能范围上限 24
local MAGIC_RANGE = 24

-- 正确：非魔法技能不受此限
local PHYSICAL_RANGE = 50  -- 物理技能可以超过 24
```

## 7. 开发原则

### 追根究底

遇到 bug 或报错，必须理解其产生原因和原有意图，从根本上解决，而非绕过。

### 按规划推进

遵循 `开发规划.md` 的任务清单逐模块开发，完成一个并通过自测后再进入下一个，复杂模块可拆分。

## 10. AI 自主决策规则

在自主执行模式下，所有设计歧义由 AI 自行决策并给出可辩护的默认选择，**禁止用"待拍板"式反问把决策推回给用户**。

### 决策总原则

1. **字面歧义按最直白解读**：需求写"敌方虫子"即 `force='enemy'`，不改成友方宠物写法
2. **性能/稳定性风险主动加保护上限，但保留用户的收益意图**：若按字面实现会导致瞬死/卡顿/实体堆积，实现方有责任主动加安全闸（如刷怪数量封顶），但**不得擅自砍掉用户明确指定的收益缩放等核心数值意图**
3. **细项一律沿用既有项目规则**：取整（`qround=math.floor`）、品质系数表（`COEFF_REG={1,1.2,1.4,1.6,1.8}`）、定时器/冷却机制等，直接复用项目已有约定
4. **描述文本维持用户原措辞**：保护上限等内部技术处理只记在代码注释里，不污染玩家可见的 locale 文案

## 审查清单

每次开发前，对照检查：

- [ ] 是否掩盖了错误（pcall / 默认值兜底 / 注释绕过）
- [ ] 调整的数字是否有明确依据（原因 + 目标值 + 依据）
- [ ] 修改已有代码前是否已向用户汇报
- [ ] 同一问题是否已尝试 2 次仍未解决（若是，立即求助）
- [ ] 添加功能前是否已搜索已有代码 → 通读完整流程 → 确认复用点
- [ ] 魔法技能/天赋的作用范围是否 ≤ 24 米
- [ ] 是否参考了已过时文档（若是，改用实际代码）
- [ ] AI 自主决策时是否遵循了字面解读 + 保护上限 + 沿用既有规则
